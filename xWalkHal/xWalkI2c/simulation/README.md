# xWalkI2c simulation

This directory contains the standalone xWalkI2c operation runner. It executes
the public I2C API and Linux backend without depending on files or functions
from `xWalkI2c/test`.

## Execution flow

```text
main
├── XWalkI2cSimulationArguments
└── XWalkI2cHandler
    └── XWalkI2c
        └── XWalkI2cLinux
            ├── XWalkI2cHostStub      build selection: stub
            └── XWalkI2cDeviceLinux   build selection: hardware
```

`XWalkI2cHandler` performs the representative operation sequence:

1. Probe address `0x14`.
2. Write bytes `0x12, 0x34` to register `0x20`.
3. Perform the fail-safe form of the same register write.
4. Read two sequential bytes.
5. Read two bytes beginning at register `0x20`.

## Build and run with the stub

The stub is the safe default. It mirrors Linux device operations in memory and
does not open `/dev/i2c-*`.

Enter the simulation submodule directory. All remaining commands in this README
use it as their working root:

```bash
cd xWalkHal/xWalkI2c/simulation
cmake -S . -B build-simulation -DXWALK_I2C_SIMULATION_BACKEND=stub
cmake --build build-simulation --target xWalkI2cSimulation --parallel
./build-simulation/xWalkI2cSimulation
```

## Build for physical hardware

The hardware selection compiles the same `main.cpp` and handler but selects the
hardware device-factory implementation. `XWalkI2cLinux` then uses
`XWalkI2cDeviceLinux` for real system calls. No backend preprocessor branch is
present in `main.cpp`.

```bash
cmake -S . -B build-hardware -DXWALK_I2C_SIMULATION_BACKEND=hardware -DXWALK_I2C_SIMULATION_DEVICE=/dev/i2c-1
cmake --build build-hardware --target xWalkI2cSimulation --parallel
```

Do not run the hardware-selected executable unless the correct Raspberry Pi and
Robot HAT are connected and it is safe to perform register writes.

When that hardware safety condition is satisfied, run the binary with all
normal traces disabled or apply one trace selector before I2C is opened:

```bash
./build-hardware/xWalkI2cSimulation
./build-hardware/xWalkI2cSimulation --help
./build-hardware/xWalkI2cSimulation --trace RPI.031.enable
./build-hardware/xWalkI2cSimulation --trace RPI.031.disable
./build-hardware/xWalkI2cSimulation --trace RPI.enable
./build-hardware/xWalkI2cSimulation --trace RPI.disable
./build-hardware/xWalkI2cSimulation --trace all.enable
./build-hardware/xWalkI2cSimulation --trace all.disable
./build-hardware/xWalkI2cSimulation --trace xwalk-traces.json
```

The selector must use the exact `RPI.<digits>.<operation>` form. An unknown UID
or malformed selector returns status `2` without opening the I2C device. The
`all` selector updates every scanner-known UID in the generated configuration.
The `--help` and `-h` options print the complete CLI contract and return without
configuring tracing or opening the I2C device.

Every compiled `RPI.<digits>` and `CTRL.<digits>` trace ID must be unique across
the project. The trace metadata build fails before C++ compilation when a
duplicate is found and reports the ID plus both source locations.

## Trace behavior

The trace generator validates and copies the immutable catalogue. Every normal
trace remains disabled by default. The executable writes enabled records to the
build-local `log/xWalkI2cSimulation.log` file.

The boot trace is initialized in `main.cpp` before the backend and handler are
constructed.

### Using the trace configuration generator

`config/xHal_Rpi5CarI2cTraceConfig.py` converts the complete trace inventory
generated by `xWalkTrace` into an xWalkI2c-specific runtime configuration. It
requires the following arguments:

| Argument | Purpose |
|---|---|
| `--input` | Existing `xwalk-traces.xml` catalogue generated by the trace scanner |
| `--output` | Destination path for the filtered xWalkI2c XML configuration |

The simulation build runs this script automatically through the default
`xWalkI2cSimulationTraceConfig` build target. The target belongs to CMake's
`ALL` build and is also an explicit dependency of `xWalkI2cSimulation`.
Therefore, both a normal build and a targeted executable build generate the
configuration. Manual execution is useful when inspecting the generated
configuration or diagnosing trace filtering. First configure the simulation
and generate the complete trace inventory:

```bash
cmake -S . -B build-simulation -DXWALK_I2C_SIMULATION_BACKEND=stub
cmake --build build-simulation --target xWalkTraceMetadata
```

Then run the generator from the simulation submodule root:

```bash
python3 config/xHal_Rpi5CarI2cTraceConfig.py --input build-simulation/generated/xwalk-traces.xml --output build-simulation/generated/xWalkI2cTrace.xml
```

The script creates the output directory when needed and reports the number of
validated all-disabled xWalkI2c traces. Generation fails if the input catalogue
contains invalid defaults or no xWalkI2c traces.

The normal `xWalkI2cSimulation` build depends on the generated file and passes
its path to the executable as `XWALK_I2C_SIMULATION_TRACE_CONFIG_PATH`, so no
manual generator command is required for ordinary simulation runs.
